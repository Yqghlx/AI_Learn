# Coding Agent 工程实践手册

> 副标题：把"会用"变成"敢用"——一套可照做的编码智能体工作方法
> 主要依据：Anthropic 官方《Best practices for Claude Code》（code.claude.com/docs/en/best-practices，抓取于 2026-10-08）
> 适用对象：1–5 年经验的一线研发工程师；也适用于要把个人提效变成团队产能的 Tech Lead

---

## 写在前面：怎么读这份手册

这份手册不是命令清单，也不是某款工具的使用说明。它回答一个工程问题：

> **当执行者从人变成模型，工程师的工作方法该怎么改？**

手册里所有"做法"都源自同一个事实约束（第 1 章）。理解了这个约束，你会发现绝大部分最佳实践是同一个道理的推论；不理解它，抄了命令也会用歪。

**三条阅读主线**

| 主线 | 回答的问题 | 章节 |
| :-- | :-- | :-- |
| 约束线 | 为什么这些方法有效？ | 第 1、5 章 |
| 单次任务线 | 一个需求从提出到合入，我该怎么做？ | 第 3、4、6 章 |
| 规模化线 | 怎么从"我一个人快"到"整个团队快"？ | 第 7、8、9 章 |

**上手最小集**：如果你只有二十分钟，做这三件事就够了——

1. 给你的仓库写一份规则文件（模板见附录 A），控制在 100 行以内；
2. 下一个任务里，强制给它一个可运行的验证命令（第 3 章）；
3. 任务串味时立刻开新会话，不要一路聊到底（第 5.4 节）。

**关于工具口径**：本手册以 Claude Code 的官方机制作为**具体载体**（字段名、命令、文件名都是真实可用的）。但这些原则本身与厂商无关——第 5.3 节末尾有一张"能力清单"，帮你把同一套方法迁移到你实际在用的工具上，无论它是 CodeBuddy、Qoder、Trae、文心快码还是任何一个带 Agent 模式的编码工具。

## 第 1 章 · 第一性原理：上下文窗口是最稀缺的资源

### 1.1 一个几乎所有最佳实践都从中推导出来的事实

> **上下文窗口装的是你整场对话：每一条消息、Claude 读过的每一个文件、每一条命令的输出。它会迅速被填满，而性能随着填充而下降。**

这不是一句抽象的提醒，它由三个可观察的现象构成：

| 现象 | 意味着什么 |
| :-- | :-- |
| 一次调试会话或一轮代码库探索，就可能产出并消耗**数万个 token** | 上下文不是慢慢用的，是几步就能烧掉一大截 |
| 窗口将满时，模型开始"遗忘"早期指令 | 你写在第一句话里的约束，可能在第 30 轮已经不起作用了 |
| 窗口将满时，犯错率上升 | 表现为"它明明知道却还是写错了"——其实它已经不"知道"了 |

**由此得到本手册最重要的一句话：**

> **上下文窗口是唯一必须被持续管理的资源。所有"最佳实践"本质上都是在争夺这块有限的空间。**

### 1.2 三条推论

理解了上面这个约束，下面这些方法就不需要记忆了——它们是自证的：

- **推论一：凡是能被移出主对话的东西，都应该移出去。**
  长期约定放进规则文件（静态加载、不占你的对话流）；偶发知识放进技能（按需加载）；重型调研交给子代理（在别处消耗，只回传结论）。
- **推论二：一次会话只解决一类问题。**
  上下文里堆积的无关历史不是"背景资料"，而是会主动降低性能的噪声。
- **推论三：不确定性靠结构消解，不靠堆字数。**
  为了让 Agent 少犯错而往提示词里塞更多解释，往往适得其反——你在花掉最贵的资源去购买边际极低的确定性。真正有效的是给出**可判定的信号**（一个能跑出 pass/fail 的命令）。

### 1.3 一个立即可做的动作

给会话加一条常驻的状态显示（例如官方推荐的自定义 status line），让上下文占用比例始终可见。

> **看不见的约束无法被管理。** 这和性能工程里"不上监控就谈优化"是同一回事。

## 第 2 章 · 心智模型：这是会用工具的执行者，不是会说话的补全器

### 2.1 先换模型，再谈技巧

Claude Code 是一个**智能体编码环境**。它和一个"回答问题然后等待"的聊天机器人的根本区别是：

> **它能读你的文件、执行你的命令、做出修改，并在你旁观、纠偏、或完全走开的情况下自主推进问题。**

这改变了分工方式：

| | 传统模式 | Agent 模式 |
| :-- | :-- | :-- |
| 你做什么 | 写代码，让 AI 检查 | 描述你要什么，由 AI 决定怎么建 |
| AI 做什么 | 返回建议文本 | 探索 → 规划 → 实施 |
| 主要瓶颈 | 敲键盘的速度 | 需求表述的精度 + 验收信号的质量 |

### 2.2 一个必须说清的误区

"自主"不等于"不需要人"。它意味着**人的工作位置变了**：

- 过去你站在**执行环节**（写代码）；
- 现在你站在**边界环节**（划定范围）和**验收环节**（定义什么叫完成）。

很多人觉得 Agent"不好用"，实际是因为他们还站在执行环节去评价它——用"它写的代码不如我手写快"来判断一个本该用"它是否替我省掉了整个下午"来衡量的东西。

### 2.3 三个阶段的范式跃迁

| 阶段 | 谁在规划 | 典型形态 |
| :-- | :-- | :-- |
| 代码补全 | 人 | 补一行、补一个函数 |
| 对话改写 | 人选片段、AI 生成 | 选中区域重构、解释、加注释 |
| 自主执行 | **AI 规划并实施，人验收** | "把这个功能做出来，跑通测试" |

> **判断**：多数人卡在第一阶段的心智里，却用第三阶段的期待去评价工具——既不放手，又要求它端到端交付，这是最常见的认知错位。

## 第 3 章 · 第一条纪律：给 Agent 一个它可以自己运行的验证

### 3.1 为什么这是第一条

> **没有验证手段时，"看起来做完了"是唯一可用的完成信号，于是你本人就成了那个验证回路——每一个错误都要等你发现。**

这句话值得反复读。它揭示的是：不给验证命令，你并没有省下验证的时间，你只是**把验证从机器串行地搬到了你自己身上**，而且是在它没有自动反馈能力的时候。

给它一个能产出信号的检查，循环就自己闭合了：**它做，它跑，它读结果，它继续改，直到通过。**

### 3.2 什么算"检查"

任何能在对话里被它读到的 **pass / fail 信号**：

- 测试套件（单元、集成、端到端）
- 构建的退出码
- Linter / 类型检查
- 一个把输出与基准文件做 diff 的脚本
- **UI 场景**：截图与设计稿对比（粘贴截图给它，让它实现后截图自查差异）

> 官方建议在它自己检查通过后，你再跑一次端到端的应用级验证（`/verify`），确认改动在真实运行环境中成立。**它的检查通过 ≠ 你的验收通过**，两者是不同层级。

### 3.3 三级递进：从"能跑"到"不用你看着"

同一件事，可以用四种力度施加，成本逐级上升、注意力逐级下降：

| 力度 | 做法 | 适用场景 |
| :-- | :-- | :-- |
| **单次提示** | 在同一条消息里要求"跑检查并迭代"，如下表三例 | 任何任务，今天就能用 |
| **会话级约束** | 把检查设为本次会话的目标条件（`/goal`），每轮后由独立评估器复核，未达成则继续 | 你想让它持续推进的中长任务 |
| **确定性闸门** | 用 Stop hook 把检查写成脚本，**不通过就不允许这一轮结束** | 必须零例外的规范（lint、格式、禁改目录） |
| **第三方复核** | 用验证子代理或动态工作流，让一个全新的模型尝试推翻结论 | 无人值守的长任务 |

> **注意**：由执行者自己评判自己的工作是有系统性偏差的。第四级的价值不在于"更严格"，而在于**让打分的人和做题的人不是同一个**。

### 3.4 三个直接可抄的改写范例

| 策略 | 改写前（避免） | 改写后（推荐） |
| :-- | :-- | :-- |
| **给出验收标准** | "实现一个校验邮箱的函数" | "写一个 `validateEmail` 函数。测试用例示例：`user@example.com` → true，`invalid` → false，`user@.com` → false。实现后运行测试。" |
| **UI 改动要视觉验证** | "把仪表盘弄好看点" | "[粘贴截图] 实现这个设计。对结果截图并与原图对比，列出差异并修复。" |
| **修根因而非压症状** | "构建挂了" | "构建失败，报错如下：[粘贴错误]。修复它并验证构建通过。处理根因，不要压制报错。" |

### 3.5 要证据，不要声明

> **让它展示证据——测试输出、它执行的命令及其返回值、结果截图——而不是断言"已完成"。**

审证据比你自己重跑一遍验证快得多，而且这条原则对你**没在旁观的会话同样有效**（这是无人值守能否成立的前提）。

在规则文件里写死这一条：

```markdown
# 汇报要求
完成任何改动后，必须附上：
1. 执行的命令原文
2. 命令的原始输出（不得改写或摘要）
3. 若为 UI 改动，附结果截图
禁止在未展示验证输出的情况下声称"已完成"。
```

## 第 4 章 · 工作流：先探索、再规划、后编码、最后提交

### 4.1 为什么要分开

> **让它直接跳出来写代码，很可能产出"正确地解决了错误的问题"的代码。**

探索和实验得分开，是因为二者的**失败成本完全不同**：探索错了，损失几轮对话；在错误方向上写完 800 行再被发现，损失的是你的信任和一下午。

### 4.2 四阶段标准动作

| 阶段 | 做什么 | 具体手段 |
| :-- | :-- | :-- |
| **① 探索** | 让它读懂相关代码，期间不得修改 | 进入计划模式（`Shift+Tab` 至状态栏显示 `⏸ plan mode on`，或启动时 `claude --permission-mode plan`） |
| **② 规划** | 让它产出详细实施方案 | 要求它列出要改哪些文件、流程是怎样的；`Ctrl+G` 在编辑器里直接修改方案 |
| **③ 实施** | 退出计划模式后让它编码 | 明确要求"按你的方案实现，并为回调处理器补测试，跑测试套件修失败" |
| **④ 提交** | 让它提交并开 PR | "用描述性的提交信息提交并开 PR" |

**探索阶段的示范提示词：**

```text
阅读 /src/auth，理解我们如何处理会话与登录。
另外看看我们是怎么管理密钥类环境变量的。
```

```text
我要接入 Google OAuth。哪些文件需要改？会话流程是怎样的？产出一份方案。
```

### 4.3 什么时候该跳过规划

计划模式有用，但也有开销。**一个句子能描述清楚的 diff，就不要开计划模式。**

直接做的情形：改错别字、加一行日志、重命名变量、单一文件的局部小修。
值得规划的情形：**你对方案不确定、改动横跨多个文件、或你不熟悉被改的那部分代码。**

> **判断**：规划的成本是固定的，收益取决于"做错方向的概率"。用它去对冲高不确定性，而不是给每个任务都上仪式。

### 4.4 一条容易被忽略的建议：让它采访你

对较大的特性，在动手之前，先让它**反过来采访你**：

```text
我想要构建 [简要描述]。用 AskUserQuestion 工具对我做详细采访。

询问技术实现、UI/UX、边界情况、顾虑和权衡。不要问显而易见的问题，
深挖我可能没考虑到的难点部分。

一直采访到覆盖全部要点，然后把完整规格写入 SPEC.md。
```

规格写完后，**开一个全新的会话去执行**——新会话上下文干净，全部注意力都在实施上，而你手上有一份书面规格可以引用。

> **什么样的规格才算好**：自包含。它点名了涉及的文件与接口、声明了什么不在范围内、并且以一个端到端的验证步骤收尾。
> **把规格改精确所花的时间，回报高于盯着它实现所花的时间。**

## 第 5 章 · 上下文工程：这门手艺的主体

本章是手册的核心。它把"上下文是稀缺资源"这一条约束，拆解成四个可操作的层次。

```
┌─────────────────────────────────────────────┐
│ ⑤ 会话层  清理 / 压缩 / 回溯 / 隔离           │  ← 治理已经进入窗口的内容
├─────────────────────────────────────────────┤
│ ④ 能力层  Skill / MCP / Hook / Subagent      │  ← 按需加载，不常驻
├─────────────────────────────────────────────┤
│ ③ 任务层  本次的任务简报（目标/上下文/约束/验收）│  ← 每次任务临时提供
├─────────────────────────────────────────────┤
│ ② 规则层  CLAUDE.md / AGENTS.md              │  ← 常驻，但必须极短
├─────────────────────────────────────────────┤
│ ① 模型层  基座能力                            │  ← 决定下限，你改不了
└─────────────────────────────────────────────┘
```

> **核心判断**：模型决定能力下限，**上下文结构决定产出上限**。团队之间真正的差距不在用哪个模型，而在规则文件和任务简报的质量。

### 5.1 任务层：把提示词写具体

> **它能推断意图，但它读不了你的心。**

四条已被验证有效的策略：

| 策略 | 改写前 | 改写后 |
| :-- | :-- | :-- |
| **限定范围**：指明文件、场景、测试偏好 | "给 foo.py 加测试" | "为 foo.py 写一个覆盖'用户已登出'边界情况的测试。不要用 mock。" |
| **指向信息源**：告诉它去哪里能找到答案 | "为什么 ExecutionFactory 的 API 这么怪？" | "翻一下 ExecutionFactory 的 git 历史，总结它的 API 是怎么演变成这样的。" |
| **引用既有范式**：指向代码库里已有的实现 | "加一个日历组件" | "先看看首页现有组件是怎么实现的，HotDogWidget.php 是个好例子。按照该范式实现一个新的日历组件，支持选择月份并可向前/向后翻页选择年份。不要引入代码库现有之外的新库。" |
| **描述症状 + 定位 + 完成定义** | "修一下登录 bug" | "用户反馈会话超时后登录失败。检查 src/auth/ 里的鉴权流程，特别是 token 刷新。先写一个能复现问题的失败测试，再修复。" |

#### 五种富内容输入方式

| 方式 | 用法 |
| :-- | :-- |
| **`@` 引用文件** | 用 `@文件路径` 代替口述代码位置，它会先读文件再回答 |
| **直接粘贴图片** | 复制粘贴或拖拽图片进提示词（UI 工作必备） |
| **给 URL** | 提供文档与 API 参考地址；常用域名可加入白名单 |
| **管道输入** | `cat error.log | claude -p "解释这个错误"` |
| **让它自己去取** | 明确告诉它可以用 Bash 命令、MCP 工具或读文件来自行获取上下文 |

> **反向用法**：模糊提示并非总是坏事。当你处于探索阶段、且付得起纠偏成本时，`"你觉得这个文件有哪些可改进之处？"` 这类问法能带出你没想到要问的东西。**明确程度应与你对任务的确定性成正比。**

### 5.2 规则层：CLAUDE.md（或 AGENTS.md）

> **这是它在每次对话开始时都会读取的特殊文件。写入那些它无法从代码中推断出来的东西：Bash 命令、代码风格、工作流规则。**

#### 起步方式

运行 `/init` 让它基于当前项目结构生成初稿，然后**长期手工打磨**。用 `/context` 确认文件确实被加载了。

#### 篇幅纪律（最重要的一条）

> **保持精简。对每一行问一句："删掉这行会导致它犯错吗？" 如果不会，就删掉。臃肿的规则文件会让它忽略你真正的指令。**

这份文件每次会话都加载，因此**只放普适的东西**。只在特定场景才用得上的领域知识或流程，放进技能按需加载，不要塞进这里撑大每一场对话。

#### 取舍清单

| ✅ 应该写 | ❌ 不该写 |
| :-- | :-- |
| 它猜不出来的 Bash 命令 | 读一遍代码就能明白的东西 |
| 与默认习惯不同的代码风格约定 | 它本来就掌握的语言通用规范 |
| 测试指令与偏好的测试运行器 | 详细的 API 文档（改为链接） |
| 仓库礼仪（分支命名、PR 规范） | 频繁变动的信息 |
| 本项目特有的架构决策 | 冗长的解释或教程 |
| 开发环境的怪癖（必需的 env var） | 逐文件的代码库描述 |
| 不自明的坑与反直觉行为 | 诸如"写整洁代码"这类正确但无用的话 |

#### 排错指南

| 症状 | 诊断 | 处理 |
| :-- | :-- | :-- |
| 明令禁止的行为仍然反复出现 | 文件太长，规则被淹没了 | 大幅删减；改用 hook 做强制约束 |
| 它问了规则里已经回答过的问题 | 该条表述有歧义 | 改写得更具体 |
| 某一条指令总是被跳过 | 缺少强调 | **只在这一行**加 `IMPORTANT`——到处强调等于没有强调 |

> **把 CLAUDE.md 当代码对待**：出问题时Review它，定期修剪，通过观察它的行为是否真的改变来验证改动是否有效。将它纳入 git，让团队共同贡献——这份文件的价值随时间复利增长。

#### 动手模板（精简版骨架）

```markdown
# 项目约定

## 构建与验证
- 构建：pnpm build（不要用 npm）
- 单元测试：pnpm test <文件>（禁止跑全量套件，太慢）
- 改动成组后必须执行类型检查：pnpm typecheck

## 代码风格
- 使用 ES modules（import/export），不用 CommonJS（require）
- 导入尽量解构：import { foo } from 'bar'

## 工作流
- 分支命名：feature/<短描述>
- 提交前跑 lint + 涉及文件的单测
- 完成改动后必须附上命令原文与原始输出作为证据

## 坑
- dev 环境必须设置 APPLICATION_KEY，否则鉴权静默失败
- migrations/ 目录需人工审核，不要直接改
```

### 5.3 能力层：Skill / MCP / Hook / Subagent / Plugin

五种扩展机制解决五类不同问题。选错工具是常见的浪费：

| 机制 | 做什么 | 什么时候用 | 例子 |
| :-- | :-- | :-- | :-- |
| **规则文件** | 每次对话都加载的常驻上下文 | 项目约定、"永远要做 X" 的规则 | "用 pnpm 不用 npm；提交前跑测试" |
| **Skill** | 它可复用的指令、知识、工作流 | 可复用内容、参考文档、重复性任务 | `/deploy` 跑部署清单；API 规范技能 |
| **Subagent** | 独立上下文，只回传摘要 | 上下文隔离、并行任务、专职角色 | 需要读大量文件但只回报关键发现的调研 |
| **MCP** | 连接外部服务 | 外部数据或动作 | 查数据库、发消息、控制浏览器 |
| **Hook** | 由事件触发的脚本/HTTP/MCP 调用 | 每次必须发生、零例外的自动化 | 每次文件编辑后跑 lint |
| **Plugin** | 打包层 | 同一套配置要在多仓库复用或分发 | 把技能+钩子+子代理+MCP 打成安装包 |

#### Skill 与 Subagent 的区别（最容易混淆的一对）

| 维度 | Skill | Subagent |
| :-- | :-- | :-- |
| **本质** | 可复用的指令/知识/工作流 | 带独立上下文的隔离执行者 |
| **核心价值** | 内容可在多上下文间共享 | **上下文隔离**：工作在别处发生，只有摘要回来 |
| **对上下文窗口的影响** | 计入你的主窗口 | 用独立窗口，有自己的输入/输出 token |

> **一句话记忆**：要共享**内容**用 Skill；要隔离**消耗**用 Subagent。

#### 渐进式搭建：不要一开始就配齐

**你不需要预先配置任何东西。** 每个机制都有一个可识别的触发信号，按下表逐步添加：

| 触发信号 | 该加什么 |
| :-- | :-- |
| 同一个约定或命令，它错了两次 | 写进规则文件 |
| 你反复要求它简短些、讲细些、或按固定格式回答 | 设置输出风格 |
| 你发现自己在反复输入同一段开场提示词 | 存成可直接调用的技能 |
| 同一份操作手册你往对话里粘贴了第三次 | 固化成技能 |
| 你不断从浏览器标签里手动复制它看不到的数据 | 把那个系统接成 MCP 服务 |
| 它为了找一个符号的定义要读很多文件 | 装对应语言的代码智能插件 |
| 某个支线任务往你的对话里灌了大量你不会再引用的输出 | 转给子代理处理 |
| 你希望某件事每次都自动发生、无需提醒 | 写个 hook |
| 第二个仓库需要同样的配置 | 打包成插件 |

> **同样的信号也告诉你何时该更新已有配置**：一个反复出现的错误或反复被提出的评审意见，应该变成规则文件的一次编辑，而不是在对话里再一次口头纠正。

#### 三个可直接抄的模板

**技能：可复用工作流**（`.claude/skills/fix-issue/SKILL.md`）

```markdown
---
name: fix-issue
description: Fix a GitHub issue
disable-model-invocation: true
---
分析并修复 GitHub issue：$ARGUMENTS。

1. 用 `gh issue view` 获取 issue 详情
2. 理解问题描述
3. 在代码库中搜索相关文件
4. 实施必要的修改
5. 编写并运行测试验证修复
6. 确保通过 lint 与类型检查
7. 写描述性的提交信息
8. 推送并创建 PR
```

> `disable-model-invocation: true` 用于有副作用、你希望手动触发的工作流。调用：`/fix-issue 1234`。

**子代理：专职审查**（`.claude/agents/security-reviewer.md`）

```markdown
---
name: security-reviewer
description: Reviews code for security vulnerabilities
tools: Read, Grep, Glob, Bash
model: opus
---
你是一名资深安全工程师。审查以下代码安全问题：
- 注入类漏洞（SQL、XSS、命令注入）
- 认证与授权缺陷
- 代码中硬编码的密钥或凭据
- 不安全的数据处理

给出具体的行号引用与修复建议。
```

> 明确点名使用：`"用一个子代理审查这段代码的安全问题。"`

**Hook：确定性约束**

Hook 与规则文件的根本区别是：**规则是建议性的，Hook 是确定性的。** 规则可能被忽略，Hook 保证动作发生。让它帮你写：

```text
写一个 hook，在每次文件编辑后自动运行 eslint
写一个 hook，禁止向 migrations 目录写入
```

### 5.4 会话层：上下文治理

> **对话是持久且可回溯的。利用这一点。**

#### 越早纠偏越好

最好的结果来自紧密的反馈循环。虽然它偶尔能一次做对，但**快速纠偏通常更快地产出更好的方案**。

| 操作 | 用途 |
| :-- | :-- |
| `Esc` | 中断它当前动作，上下文保留，可立即改向 |
| `Esc + Esc` 或 `/rewind` | 打开回溯菜单，恢复之前的对话/代码状态，或从选定消息处压缩 |
| `"撤销那个"` | 让它回退改动 |
| `/clear` | 在不相干的任务之间重置上下文 |

> **硬规则**：**同一问题上你纠正超过两次，就必须 `/clear` 重开。** 此时上下文里已经塞满了失败方案。带着学到的东西写一个更好的初始提示词，干净会话几乎总是优于一个堆满纠正的长会话。

#### 主动压缩

到达上限前它会自动压缩历史，保留重要代码与决策并释放空间。你也可以主动控制：

- `/clear` 频繁地在任务间彻底重置；
- `/compact <指令>` 定向压缩，例如 `/compact 聚焦 API 改动`；
- `Esc + Esc` 或 `/rewind` 选择检查点，用"从此处压缩" / "压缩到此为止"做局部压缩；
- **把压缩偏好写进规则文件**，例如：`"压缩时，务必保留完整的已修改文件清单与所有测试命令"`；
- 不需要留在上下文里的一次性疑问用 `/btw` 提问——答案不进对话历史，因此既能查细节又不增长上下文。

#### 检查点：放心让它试错

> **你不必精心规划每一步。可以告诉它去试一个冒险的方案；不行就回溯，换条路。**

每次你发出开始新一轮的消息都会创建检查点。双按 `Esc` 或 `/rewind` 打开回溯菜单，可分别恢复**仅对话 / 仅代码 / 两者全部**。检查点随会话保存，因此关掉终端、之后恢复会话，依然可以回溯。

> ⚠️ **重要限制**：检查点只追踪**通过它自身的文件编辑工具**做出的改动。通过 Bash 命令或外部进程产生的修改不会被捕获。**检查点不能替代 git。**

#### 把调研外包出去

> **上下文是根本约束，因此用子代理把调研挡在外面。**

它调研代码库时会读大量文件，全部消耗你的上下文。子代理在独立上下文窗口里跑，只回传摘要：

```text
用子代理去调研我们的鉴权系统如何处理 token 刷新，
以及是否已有可复用的 OAuth 工具函数。
```

#### 会话命名：像管理分支一样管理会话

会话本地保存，跨多次开工不必重复解释背景。`claude --continue` 接着上次继续，`claude --resume` 从列表里选。

> **给它起描述性的名字**（`/rename oauth-migration`），**并把会话当作分支对待——每条工作流拥有自己的持久上下文。**

### 5.5 通信：像对待一位资深同事那样提问

就这个层级的 Agent 而言，最容易被低估的用法是**把它当作随时可问的同事**：

- 日志是怎么工作的？
- 我要新增一个 API 端点该怎么做？
- `foo.rs` 第 134 行的 `async move { ... }` 是干什么的？
- `CustomerOnboardingFlowImpl` 处理了哪些边界情况？
- 为什么第 333 行调用的是 `foo()` 而不是 `bar()`？

> 用这种方式做新人 onboarding，**能显著缩短上手时间并减少对其他工程师的打扰**。不需要特殊提示词，直接问就行。

## 第 6 章 · 权限与安全：先画笼子，再放它出去

### 6.1 两难与解法

每次都弹窗确认 = 安全但烦人。**点过第十次以后你就不再是审查，而只是在点。** 真正有效的注意力是稀缺的，不要把它消耗在低价值的点击上。

两条互补的手段：

| 手段 | 作用 | 适用工具 |
| :-- | :-- | :-- |
| **权限白名单** | 预批准你信任的具体工具，如 `npm run lint`、`git commit` | `/permissions` |
| **沙箱隔离** | 操作系统级隔离，限制文件系统与网络访问，让它在边界内自由工作 | `/sandbox` |

### 6.2 权限模式速查

| 模式 | 行为 | 何时用 |
| :-- | :-- | :-- |
| **Auto（自动）** | 由独立分类模型代替你复核大多数操作，只拦截看起来有风险的（越权、未知基础设施、受恶意内容驱动的动作） | 日常默认（v2.1.283 起为交互式终端与 VS Code 会话的内置起始模式） |
| **Manual（手动）** | 修改系统的动作前都询问：文件写入、Bash 命令、MCP 工具 | 你想自己批准每一次改动时 |
| **Plan（计划）** | 只读 + 规划，不落任何修改 | 探索与方案阶段 |
| **dontAsk** | 只放行已预批准的工具，其余一律拒绝 | 无人值守的批量运行 |

> 无头运行（`-p`）时若分类模型反复拦截，**运行不会自动停止**——具体回退行为与阈值见官方文档。这一点在把它接进 CI 前必须确认。

### 6.3 用 Hook 做"零例外"的护栏

**建议性的规则会被忽略，Hook 不会。** 凡是不可妥协的约束，都应该从规则文件升级为 Hook：

- 禁止写入某些目录（迁移目录、密钥目录）
- 每次编辑后强制 lint / 格式化
- 提交前强制跑测试
- 阻断包含敏感模式的操作

### 6.4 四条不可让步的底线

| 底线 | 说明 |
| :-- | :-- |
| **沙箱隔离** | 文件系统与网络必须有边界，不要让它在你的主环境裸奔 |
| **最小权限** | 只放行必要的工具；批量运行前用 `--allowedTools` 显式声明 |
| **全程可审计** | 能回答"它改了什么、执行了什么命令"；Hook 与会话日志是审计基础 |
| **危险动作人工审批** | 涉及数据变更、部署、密钥的动作保留人工闸门 |

> **判断：便利来自权限，风险同样来自权限。先画笼子再放它出去，顺序不能颠倒。**

### 6.5 一条常被忽略的推论

> **如果它产出了一个看似合理但不处理边界情况的实现——那么问题通常不在模型，而在你没给它验证方式。**
> 无法验证的东西，不要上线（第 3 章）。这与第 6 章是同一件事的两面：**验证是质量的闸门，权限是安全的闸门。**

## 第 7 章 · 规模化：从一个人快到整个团队快

> 前提：**先让一个 Claude 用得有效，再用并行会话、无头模式和扇出模式把产出成倍放大。** 顺序反了，只会把低效复制 N 份。

### 7.1 无头模式：把它接进流水线

```bash
# 一次性查询
claude -p "解释这个项目是做什么的"

# 供脚本解析的结构化输出（返回带 result 字段的单个 JSON 对象）
claude -p "列出所有 API 端点" --output-format json

# 流式输出，便于实时处理（每行一个 JSON 对象，以 init 事件开头）
claude -p "分析这个日志文件" --output-format stream-json --verbose

# 接进现有数据管道
claude -p "<你的提示词>" --output-format json | your_command
```

> 除非传 `--no-session-persistence`，否则无头运行**同样会创建可恢复的会话**——这对 CI 里的问题复盘很有用。

### 7.2 并行会话的六种形态

按你想亲自协调的程度选择；当会话之间需要传递发现时，再加上跨会话消息：

| 形态 | 适用 |
| :-- | :-- |
| **Git worktrees** | 独立检出中运行隔离会话，改动不会互相覆盖 |
| **跨会话消息** | 你自己跑的多个会话之间互相传递发现 |
| **桌面应用** | 可视化管理多个本地会话，各自可在独立 worktree |
| **云端运行** | 在托管基础设施上运行会话 |
| **Agent view**（预览） | `claude agents` 派发后台会话，在一个屏幕里统一观察 |
| **Agent teams**（实验性，默认关闭） | 多会话自动协调：共享任务、消息、团队负责人 |

### 7.3 Writer / Reviewer：并行带来的最大质量红利

> **除了提速，多会话还支撑了以质量为目标的工作流：全新上下文能提升代码评审质量，因为它不会偏向自己刚写出来的东西。**

| 会话 A（Writer） | 会话 B（Reviewer） |
| :-- | :-- |
| `为我们的 API 端点实现限流器` | |
| | `审查 @src/middleware/rateLimiter.ts 中的限流实现。关注边界情况、竞态条件，以及与现有中间件范式的一致性。` |
| `这是评审意见：[会话 B 的输出]。处理这些问题。` | |

同样的模式可用于测试：**让一个写测试，另一个写代码去通过它。**

### 7.4 扇出：大规模迁移与分析

把工作分发到大量并行调用上。可用内置 `/batch <指令>`（把改动拆分给 5–30 个子代理，**每个在独立 worktree 中工作**），或用你自己的脚本循环调用 `claude -p`：

**第 1 步 · 生成任务清单**

```text
列出所有需要迁移的 2000 个 Python 文件，把清单保存到 files.txt
```

**第 2 步 · 写循环脚本**

```bash
for file in $(cat files.txt); do
  claude -p "把 $file 从 Python 2 迁移到 Python 3。返回 OK 或 FAIL。" \
    --allowedTools "Edit,Bash(git commit *)" \
    --permission-mode dontAsk
done
```

**第 3 步 · 先小批量试，再全量跑**

根据前 2–3 个文件暴露的问题**调整提示词**，再跑全量。`--allowedTools` 预批准迁移所需的工具，`--permission-mode dontAsk` 拒绝任何还需要审批的操作——**这在无人值守运行时至关重要**。

### 7.5 无人值守：auto 模式

```bash
claude --permission-mode auto -p "修复所有 lint 错误"
```

分类模型会在命令执行前复核，拦截越权、未知基础设施与恶意内容驱动的操作，同时让日常改动无需弹窗推进。

### 7.6 对抗式评审：为长任务上保险

> **它无人值守工作得越久，认定为完成之前就越需要一次独立检查。**

在全新子代理上下文里跑的评审者，只看到 diff 和你给的判定标准，**看不到产生这段改动的推理过程**，因此它会按自己的标准评估——这正是它有价值的原因。

内置选项：跑 `/code-review`，在全新子代理里审查当前 diff 的缺陷并把发现带回会话。
自定义选项（对照计划而非只看正确性）：

```text
用一个子代理对照 PLAN.md 审查限流器的 diff。
检查每一条需求都已实现、列出的边界情况都有测试、
且任务范围之外的东西没有被改动。只报告缺口，不讲风格偏好。
```

> ⚠️ **反向陷阱**：**被要求"找缺口"的评审者几乎总会报告一些缺口，即使工作本身是健全的**——因为那是你交给它的任务。逐个追查会导致过度工程：多余的抽象层、防御性代码、以及为不可能发生的情况写的测试。
> **明确告诉评审者只标记影响正确性或违反既定需求的缺口，其余视为可选项。**

## 第 8 章 · 七个高频失败模式与对症修正

前五个是官方明确点名的高频错误，后两个是工程落地时同样常见的衍生物。

| # | 失败模式 | 机理 | 修正 |
| :- | :-- | :-- | :-- |
| 1 | **大杂烩会话**：从一个任务开始，中间问了不相干的事，再回到第一个任务 | 上下文塞满无关信息 | **无关任务之间执行 `/clear`** |
| 2 | **反复纠正**：它做错，你纠正，还错，你再纠正 | 上下文被失败方案污染 | **两次纠正失败后 `/clear`，带着学到的东西重写初始提示词** |
| 3 | **过度指定的规则文件**：写得太长，它忽略其中一半 | 重要规则淹没在噪声里 | **无情修剪**。若某件事它不用指令也能做对，删掉该行或升级为 hook |
| 4 | **信任—验证缺口**：产出看似合理但不处理边界情况的实现 | 你没给验证手段，于是它只能以"看起来像"为准 | **始终提供验证（测试/脚本/截图）。无法验证就不要上线** |
| 5 | **无限探索**：让它"调研一下"而没限定范围，它读了上百个文件塞满上下文 | 调研消耗被计入主窗口 | **收窄调研范围，或交给子代理** |
| 6 | **规格未固化就开工**：口述需求、边做边改 | 每次口头纠偏都同时污染上下文与代码 | 大特性先让它采访你并产出 SPEC.md，**再开新会话执行** |
| 7 | **把 `--allowedTools` 配成"全放行"**：为了省事给批量任务开全权限 | 便利与风险同源 | 批量运行时**只预批准必需的具名工具**，配合沙箱与 `dontAsk` |

> **通用诊断顺序**：它表现不好时，按此顺序自查——**上下文是否太脏？提示词是否太糊？任务是否大到不该一次跑完？验证信号是否存在？** 八成问题落在这四条的某一条上。

## 第 9 章 · 落地路径与度量：从个人习惯到团队规范

### 9.1 90 天路线图

| 阶段 | 目标 | 交付物 | 完成判定 |
| :-- | :-- | :-- | :-- |
| **第 1 个 30 天** | 建规范 | 仓库内的规则文件（<100 行）+ 3 个高频技能 + 2 个确定性 Hook | 新人在空仓库照规则文件能跑通一次完整改动 |
| **第 2 个 60 天** | 跑试点 | 1–2 个真实需求的端到端案例（含 spec、diff、验证输出、评审记录） | 复盘能说清：哪些环节省了时间，哪些环节把时间还回去了 |
| **第 3 个 90 天** | 进流水线 | CI 中的无头调用（`-p` + `--output-format json`）+ 提交前 Hook + 权限白名单基线 | 无人值守任务有失败告警，且有回滚路径 |

> **顺序不能颠倒：先统一规则文件，再谈覆盖率。** 没有共享约定就推广工具，只会把每个人的个人习惯放大成团队的不可维护性。

### 9.2 该看的四个指标

| 指标 | 衡量什么 | 为什么是它 |
| :-- | :-- | :-- |
| **采纳率** | 团队实际使用比例与频次 | 不好用的东西推广不动，这是前置指标 |
| **返工率** | 产出物被人工推翻/重写比例 | 直接反映上下文质量（规则文件 + 任务简报） |
| **缺陷密度** | 单位改动引入的缺陷数 | 防止"速度换质量"的自欺 |
| **端到端时长** | 需求提出到合入的墙钟时间 | 唯一能证明"整体更快"的指标，而非"写函数更快" |

> **警告：只统计"生成了多少代码"会奖励错误行为。** 它会激励产出更多代码，而产出更多代码从来不是工程目标。

### 9.3 五个组织层面的高频误区

1. **比参数不作 PoC** —— 横评数据都来自厂商场景，唯一可信的判断来自**你自己的代码库**。
2. **一次性全员铺开** —— 应先建立规则基线，再做小范围试点并复盘。
3. **只培训操作不培训验收** —— 会发指令不等于会验收；后者才是新的核心技能。
4. **把僵尸规则堆进规则文件** —— 只增不删的文件会反向劣化所有人的产出。
5. **跳过验证直接接入 CI** —— 没有 fail 信号的自动化会把错误静默地批量化。

## 第 10 章 · 培养直觉：什么时候该打破规则

> **这套模式不是金科玉律。它们是一般有效的起点，未必在每种情形下都最优。**

以下"例外"和上面的"规则"同样重要：

- **有时你应该让上下文累积** —— 当你深陷一个复杂问题，历史本身是有价值的；
- **有时你应该跳过规划** —— 任务本身是探索性的，让它边做边找答案；
- **有时模糊提示恰恰是对的** —— 你想先看到它如何解释问题，再施加约束。

> **留意什么有效。** 当它产出优秀结果时，注意你当时做了什么：提示词的结构、提供的上下文、所处的模式。当它挣扎时，问为什么——上下文太吵？提示词太糊？任务大到不该一次跑完？

**随着时间推移，你会发展出任何指南都无法传授的直觉**：你知道何时该具体、何时该开放，何时该规划、何时该探索，何时该清空上下文、何时该让它累积。

## 附录 A · 规则文件模板（可直接复制，务必裁剪）

```markdown
# <项目名> 约定

## 环境
- 包管理器：pnpm（禁止 npm / yarn）
- Node 版本：见 .nvmrc
- 必需环境变量：见 .env.example；缺 APPLICATION_KEY 会导致鉴权静默失败

## 构建与验证
- 构建：pnpm build
- 类型检查：pnpm typecheck
- 单测（指定文件）：pnpm test <path>
- 禁止在改动验证中使用全量测试套件（耗时过长）

## 代码风格
- ES modules（import/export），不用 CommonJS
- 导入尽量解构：import { foo } from 'bar'
- 命名：<项目特有约定，写明与默认习惯不同之处>

## 工作流
- 分支：feature/<短描述> | fix/<短描述>
- 提交信息：<约定格式>
- 每次改动成组后必须 typecheck + 受影响文件的单测

## 汇报要求（强制）
完成后必须附上：
1. 执行的命令原文
2. 命令原始输出（不得摘要或改写）
3. UI 改动附结果截图
禁止在未展示验证输出的情况下声称完成。

## 边界
- migrations/ 与 .github/ 需人工审批，不得自动修改
- 禁止修改任何含密钥的文件

## 压缩偏好
压缩时务必保留：完整的已修改文件清单、所有测试命令、当前任务目标。
```

> **自检**：逐行问"删掉这行会让它犯错吗？"。答不上来的行，删掉。**目标：不超过 100 行。**

## 附录 B · 任务简报模板

```markdown
## Goal（要什么）
一句话说清终点。

## Context（在哪儿）
- 相关文件/模块：<具体路径，而非"那个服务">
- 既有范式：<指向一个可参考的现成实现>
- 背景成因：<为什么现在要做这件事>

## Constraints（不能做什么）
- 技术：不得引入现有之外的新依赖 / 不得使用 mock / ...
- 范围：只改 <路径>，不得触碰 <路径>
- 风格：遵循 <文件> 中的范式

## Done-when（什么叫完成）
1. 命令 `<具体命令>` 退出码为 0
2. 测试用例 <具体输入 → 期望输出> 全部通过
3. <若为 UI> 结果截图与原设计稿差异已逐条列出并修复
```

**一句话自检**：把 Done-when 盖住，如果你无法判断别人写的这部分是否完成，说明它还不够具体。

## 附录 C · 速查表

### 键盘与命令

| 操作 | 作用 |
| :-- | :-- |
| `Esc` | 中断当前动作（保留上下文） |
| `Esc + Esc` / `/rewind` | 回溯菜单：恢复对话/代码/两者，或局部压缩 |
| `Ctrl+G` | 在编辑器中打开当前计划进行直接编辑 |
| `Shift+Tab` | 切换权限模式（含计划模式） |
| `/init` | 生成规则文件初稿 |
| `/context` | 确认规则文件已加载 |
| `/doctor` | 让它提出规则文件的删减建议 |
| `/permissions` | 配置权限白名单 |
| `/sandbox` | 配置沙箱 |
| `/hooks` | 浏览已配置的钩子 |
| `/clear` | 重置上下文（**要用得比你以为的更频繁**） |
| `/compact <指令>` | 定向压缩 |
| `/btw` | 提问但不进入对话历史 |
| `/rename <名字>` | 命名当前会话 |
| `/batch <指令>` | 拆分为 5–30 个子代理并行执行 |
| `/code-review` | 全新子代理审查当前 diff |
| `/verify` | 端到端验证运行中的应用 |
| `claude -p "<prompt>"` | 无头模式 |
| `claude --continue` / `--resume` | 恢复会话 |
| `claude --permission-mode plan/auto/dontAsk` | 指定权限模式启动 |

### 决策速查

| 情境 | 动作 |
| :-- | :-- |
| 同一问题纠正了两次 | `/clear` 重开，带着结论重写提示词 |
| 它在 Read 大量文件做调研 | 换子代理 |
| 你第三次粘贴同一份操作手册 | 固化成技能 |
| 你想 CONDITIONS 每次强制发生 | Hook（不是规则文件） |
| 长任务无人值守后要认定完成 | 独立子代理做对抗式评审 |
| 批量任务不想被弹窗打断 | `--allowedTools` 具名放行 + `--permission-mode dontAsk` + 沙箱 |
| 不知道它改进得对不对 | 缺验证信号 → 补一条能跑出 pass/fail 的命令 |

## 附录 D · 迁移到其它编码工具的能力清单

本手册以 Claude Code 的机制作为**具体载体**，但原则与厂商无关。换工具时，按这张清单逐项确认目标工具是否具备对应能力——**有，就把这套方法照搬过去；没有，就找出替代实现。**

| 能力 | 在本手册中的位置 | 需要工具支持的形态 |
| :-- | :-- | :-- |
| 常驻规则文件 | 5.2 | 仓库级约定文件，每次会话自动加载（如 CLAUDE.md / AGENTS.md 类机制） |
| 上下文占用可视化 | 1.3 | 会话内可见的用量显示 |
| 可中断 + 可回溯 | 5.4 | 中断执行、恢复对话/代码状态的能力 |
| 上下文压缩/清理 | 5.4 | 手动与自动的历史压缩 |
| 只读计划模式 | 4.2 | 允许探索与规划但禁止写入的模式 |
| 可复用工作流（技能） | 5.3 | 可按需加载或手动调用的指令/手册单元 |
| 独立上下文执行（子代理） | 5.3 / 5.4 / 7.6 | 任务在隔离上下文中执行、只回传摘要 |
| 外部系统连接 | 5.3 | 等效于 MCP 的工具扩展接口 |
| 事件触发的确定性钩子 | 5.3 / 6.3 | 在特定事件必然触发的脚本或回调 |
| 权限白名单与沙箱 | 6.1 / 6.2 | 具名工具放行 + 文件系统/网络隔离 |
| 无头/流水线调用 | 7.1 | 命令行非交互调用 + 结构化输出 |
| 并行与隔离 | 7.2 / 7.4 | 多会话并行，且改动互不覆盖（如 worktree 等效机制） |

> **提示**：不同产品对上述能力的命名与开放程度差异较大，实际配置方式请以你所用工具的官方文档为准。这份清单的作用是**确保你没有漏掉某一层**，而不是替代产品文档。

## 附录 E · 本周就能开始的三件事

1. **今天**：为你的主仓库写一份规则文件（附录 A），删到 100 行以内，纳入 git。
2. **本周**：挑一个真实的小需求，用"任务简报模板"（附录 B）跑一轮——**必须包含一个能跑出 pass/fail 的验证命令**。
3. **本周**：为一个你重复了三次以上的操作，创建一个可复用技能（5.3 模板）。

> **收束**：这套方法的终点不是"让 AI 写代码"，而是**把团队的工程默契从人的脑子里搬进仓库**。
> 一旦约定落到了文件里，它就开始复利——新人不问人也能知道规范，几个月后的你也记得当初为什么这么定。
