== P07
   五类形态：先认形态，再看品牌
   形态决定能力边界，品牌只决定细节
   形态
   代表产品
   擅长
   代价 / 边界
   IDE 插件
   Copilot · 通义灵码 · CodeBuddy
   嵌入现有编辑器：补全、解释、局部重构，零迁移成本
   受编辑器边界约束；跨文件长任务与流水线能力弱
   命令行智能体
   Pi · Claude Code · Codex CLI · OpenCode
   直接操作仓库与终端，易脚本化，可无头进 CI
   无可视化界面；上手曲线陡；长任务要自己治理上下文
   编辑器内核分叉
   Cursor · Trae
   编辑器与智能体深度耦合，既有配置可一键迁移
   团队工具链被锁定；版本节奏跟随厂商
   桌面工作台
   腾讯 WorkBuddy · Qoder 工作台
   一人指挥多个专家智能体并行，适合复杂需求
   上下文与 token 消耗高；可复现性与可控性挑战
   云端智能体平台
   Codex Cloud · Antigravity · Qoder 云端

== P08
   怎么选：三步，一步一句话
   先划掉不能用的，再按工作方式定形态，最后用真实任务验证
   01
   排除 · 把不能用的先划掉
   代码不能出网 → 不用云端平台；必须自托管 / 可换模型 → 只走开源路线；深度绑定某个 IDE → 优先该 IDE 的插件或内核分叉
   02
   定形态 · 你要它替你做到哪一步
   只要补全与解释 → IDE 插件；要它自己跑完并自验 → 命令行 或 桌面工作台；要它异步跑完直接交 PR → 云端平台
   03
   验证 · 同类里挑哪个，别靠感觉
   同一批真实任务 + 同一套可运行验收（跑测试 / 跑构建），跑满两周再定——第一天的新鲜感会骗人
   结论
   统一比最优重要：团队选型的产出不是「选到最好的那个」，而是「大家用同一个」——规则文件、技能库、钩子配置都要沉淀在同一套工具上。下一章要看真实会话，会提到工具名；从第 3 章起，后面四章不再提产品名，也不依赖你选了谁。

== P12
   一个约束：上下文窗口是稀缺资源
   它是唯一必须持续管理的东西——几乎所有最佳实践都从这条事实推导出来
   现象 01
   消耗极快
   一次调试会话或一轮代码库探索，就可能产出并消耗数万个 token——上下文不是慢慢用的，是几步就能烧掉一大截。
   现象 02
   开始“遗忘”
   窗口将满时，模型开始遗忘你在第一句写下的指令——你以为它记得的约束，可能已经不起作用了。
   现象 03
   犯错率上升
   表现为“它明明知道却还是写错了”——其实它已经不“知道”了。这不是模型变笨，是窗口太满。
   推论一 · 能移出去的都移出去
   长期约定进规则文件，偶发知识进技能，重型调研交给子智能体——主对话只留本次任务。
   推论二 · 一次会话一类问题
   堆积的无关历史不是背景资料，是会主动降低性能的噪声。任务串味时，立刻开新会话。
   推论三 · 不确定性靠结构消解
   只堆更多解释，等于花最贵的资源买边际极低的确定性。真正有效的是可判定的信号。
   上下文窗口装着整场对话：你的每条消息、它读过的每个文件、每条命令的输出。
   结论
   把不该留在窗口里的挪出去（推论一、二），把留下来的花在能判定对错的东西上（推论三）。前提是它得可见——看不见的约束，谈不上管理。

== P13
   一种心智：从“帮你写”到“替你做”
   “自主”不等于不需要人——它意味着人的工作位置变了
   阶段一
   代码补全
   人在写，AI 猜下一个词。Tab 键就是全部交互，出错成本极低。
   阶段二
   对话改写
   人规划，AI 生成整段。选中-提问-粘贴，心智仍是“我来改”。
   阶段三
   自主执行
   AI 拆任务、调工具、改文件、跑测试；人定边界、给约束、做验收。
   分工的变化   同一个需求，两种工作方式
   你的角色
   过去 · 执行环节：亲手写代码
   现在 · 边界环节（划定范围）＋ 验收环节（定义“完成”）
   AI 的角色
   过去 · 返回建议文本，看完还得你来改
   现在 · 探索、规划、实施，自己跑验证
   主要瓶颈
   过去 · 你敲键盘的速度
   现在 · 需求表述的精度＋验收信号的质量
   结论
   变的是人的位置，不是人的必要性：过去在执行环节，现在在边界和验收环节。评价标准也要跟着换——不是「写得快不快」，而是「有没有省掉整个下午」。

   一次需求，四个标准动作
   给可运行的验证、先探索再编码、让它采访你、规格先行——四件事，把“玄学体验”变成“稳定产出”。
== P15
   第一条纪律：给它一个可运行的验证
   没有验证手段时，“看起来做完了”是唯一信号——于是你本人成了验证回路
   现场演示
   没有验证
   它只能以“看起来像”为准。每个错误都等你发现——你把验证从机器搬回了自己身上，而且是串行的。
   给它一个能读出 pass / fail 的信号
   测试套件、构建退出码、Linter、输出对比脚本、UI 截图比对。它做、它跑、它读结果、它继续改——循环自己闭合。
   注意：它的检查通过 ≠ 你的验收通过——两者是不同层级，上线前你仍需端到端确认。
   结论
   要证据，不要声明：完成后必须附上命令原文与原始输出（UI 改动附截图）。审证据比重跑验证快得多，且对你没在旁观的会话同样有效。
   4
   级验证闸门 逐级降低你的注意力消耗
   L1 · 单次提示
   同一条消息里要求“跑检查并迭代”——任何任务，今天就能用。
   L2 · 会话级目标
   由独立评估器每轮复核目标是否达成，未达成则继续——中长任务。
   L3 · 确定性闸门
   用脚本钩子在轮次结束前强制检查，不通过不许停——零例外的规范。
   L4 · 第三方复核
   全新上下文的评审智能体：做题的人，不是打分的人——无人值守。

== P16
   提示词改写：三组实战对照
   加约束比加形容词有效——每一组“好”，都附带了可判定的验收
   现场演示
   ✕  改写前
   实现一个校验邮箱的函数
   ✓  改写后 · 给出验收标准
   写一个 validateEmail：user@example.com → true、invalid → false、user@.com → false。实现后运行测试，直到全部通过。
   ✕  改写前
   把仪表盘弄好看点
   ✓  改写后 · UI 改动要视觉验证
   按这张设计稿实现（附截图）。完成后对结果截图并与原图对比，逐条列出差异并修复。
   ✕  改写前
   构建挂了
   ✓  改写后 · 修根因，不压症状
   构建失败，报错如下（粘贴完整错误）。修复并验证构建通过——处理根因，不要压制报错。
   结论
   一句话自检：把“完成定义”盖住——如果你无法判断这部分是否算完成，它就还不够具体。

== P17
   单次任务的标准动作
   探索 → 规划 → 编码 → 提交——分开，是因为两段旅程的失败成本完全不同
   现场演示 ×3
   01
   探索
   只读模式下读懂相关代码，期间不得修改。让它讲清现状，而不是急着动手。
   02
   规划
   产出实施方案：改哪些文件、流程是什么。人可以直接修改方案再批准。
   03
   编码
   退出只读，按方案实现；为新逻辑补测试，跑到通过为止。
   04
   提交
   描述性提交信息，开 PR，附验证输出作为证据。
   何时跳过规划
   直接做：改错别字、加日志、重命名、单文件局部小修。
   值得规划：你对方案不确定 / 改动横跨多文件 / 你不熟悉被改的那部分代码。
   判据：一句话能描述清楚的 diff，就不要上仪式。
   结论
   规划的成本是固定的，收益取决于“做错方向的概率”——用它对冲高不确定性，而不是给每个任务都上流程。探索错了，损失几轮对话；在错误方向写完 800 行再被发现，损失的是你的信任和一下午。

== P18
   大特性起手式：先让它采访你
   不确定的地方不该让它猜，该让它问——把规格改精确，回报高于盯着实现
   1
   发出采访邀请
   “我想构建 X。请详细采访我：技术实现、UI/UX、边界情况、顾虑与权衡。不问显而易见的，深挖我可能没考虑到的。”
   2
   产出自包含 SPEC
   规格写进文件：点名涉及的文件与接口，声明什么不在范围内，以端到端验证步骤收尾。
   3
   开新会话执行
   干净上下文，全部注意力给实施。书面规格随时可引用、可评审、可交接。
   什么样的规格才算好
   自包含 · 不读对话记录也能看懂——别人（和未来的你）可以直接接手
   有边界 · 明确写下“什么不做”——范围蔓延是 Agent 返工的最大来源
   可验收 · 以端到端验证步骤收尾——完成与否，跑一条命令就知道
   结论
   口述需求、边做边改，会让每一次口头纠偏同时污染上下文与代码——规格未固化就开工，是最高频的失败模式之一。把规格写精确所花的时间，回报高于你盯着它实现所花的时间。

   产出差距在上下文结构，不在模型
   同一个模型，在不同团队手里产出天差地别。差距来自四层：规则怎么沉淀、任务怎么写、能力怎么扩展、会话怎么治理。自底向上讲。
== P20
   上下文工程：这门手艺的主体
   五层结构——把静态约束从提示词里搬出去，主线程只留本次任务契约
   ⑤
   会话层  治理
   清理、压缩、回溯、子智能体隔离——管理已进入窗口的内容
   ④
   能力层  按需
   技能、子智能体、外部工具、事件钩子——不常驻，需要时才加载
   ③
   任务层  临时
   本次的任务简报：目标、上下文、约束、验收——每次任务临时提供
   ②
   规则层  常驻
   每次会话都加载的项目约定——必须极短，只放普适的东西
   ①
   模型层  底座
   基座推理与代码能力——决定下限，我们换不了（第 3 章已讲过）
   同一个模型，在不同团队手里产出天差地别——差距几乎都出在 ②③④：规则写得准不准、简报给得清不清、能力接得全不全。
   模型的差距是线性的，上下文结构的差距是乘性的。
   结论
   模型决定下限，上下文结构决定上限。换模型不如补上下文——这是这门课最值钱的一句话。

== P21
   规则层：把默契写进仓库
   每次会话都加载——所以只放普适的东西，并且必须极短
   ✓ 应该写
   它猜不出来的构建/测试命令
   与默认习惯不同的代码风格
   测试指令与偏好的运行器
   仓库礼仪：分支命名、PR 规范
   本项目特有的架构决策
   环境怪癖与不自明的坑
   ✕ 不该写
   读一遍代码就能明白的东西
   语言通用规范（它本来就会）
   详细 API 文档（改为给链接）
   频繁变动的信息
   逐文件的代码库描述
   “写整洁代码”式正确废话
   篇幅纪律（最重要）
   对每一行问：“删掉这行会让它犯错吗？” 答不上来就删。臃肿的规则会让它忽略你真正的指令——目标 < 100 行。
   排错指南
   明令禁止仍反复出现
   → 文件太长，规则被淹没：剪
   问了规则里已答的问题
   → 表述有歧义：改写得更具体
   单条指令总被跳过
   → 只在这一行加强调，别处处加
   结论
   把它当代码对待：出问题就审查、定期修剪、用“行为是否真的改变”验证改动。纳入 git 团队共建——这份文件的价值随时间复利增长。

== P22
   任务层：把提示词写具体
   它能推断意图，但读不了你的心——四种策略，一份简报
   现场演示
   限定范围
   “为 foo.py 写一个覆盖‘用户已登出’边界情况的测试。不要用 mock。”
   指向信息源
   “翻一下这个类的 git 历史，总结它的 API 是怎么演变成这样的。”
   引用既有范式
   “参照首页既有组件的实现范式来做日历组件，不引入新依赖。”
   症状+定位+验收
   “会话超时后登录失败。检查 auth 模块的 token 刷新，先写复现的失败测试再修。”
   五种方式喂给它富上下文
   引用文件（@路径）
   粘贴截图 / 设计稿
   提供文档 URL
   管道喂数据（日志、报错）
   让它自己去取（读文件/跑命令/调工具）
   任务简报四要素
   Goal
   要什么——一句话说清终点
   Context
   在哪儿——具体路径，指向既有范式
   Constraints
   不能做什么——依赖、范围、风格
   Done-when
   什么叫完成——可运行、可判定
   结论
   明确程度与任务确定性成正比：探索期可以用模糊提示找灵感（“你觉得这个文件有哪些可改进？”），交付期必须给出可判定的验收。

== P23
   能力层：五种扩展机制，别选错工具
   要共享内容用技能；要隔离消耗用子智能体——选错是常见的浪费
   最易混淆的一对
   技能 = 可复用内容，加载进你的主窗口
   子智能体 = 隔离执行者，独立上下文，只回传摘要
   结论
   内容由技能承载，消耗由子智能体隔离。分不清这一对，等于把全部调研成本压在自己的主上下文里——窗口就是这么被悄悄吃掉的。

== P24
   渐进式搭建：让问题触发配置
   你不需要预先配置任何东西——每个机制都有一个可识别的触发信号
   触发 · 同一个约定或命令，它错了两次
   写进规则文件
   触发 · 你反复输入同一段开场提示词
   存成可直接调用的技能
   触发 · 同一份操作手册粘贴了第三次
   固化成技能
   触发 · 手动从浏览器复制它看不到的数据
   把那个系统接成外部工具
   触发 · 它为找一个符号要读很多文件
   装代码智能插件
   触发 · 支线任务灌入大量不再引用的输出
   转给子智能体
   触发 · 希望某件事每次自动发生、无需提醒
   写成事件钩子
   触发 · 第二个仓库需要同样的配置
   打包成插件分发
   配 置 顺 序 由 问 题 定
   结论
   同样的信号也告诉你何时更新：一个反复出现的错误，应该是规则文件的一次编辑，而不是对话里的又一次口头纠正。

== P25
   会话层：上下文治理
   清理、压缩、回溯是你的日常操作——不是急救手段
   硬规则：同一问题上纠正了两次 → 立刻清理上下文，重开会话
   此时上下文已塞满失败方案。带着学到的东西写一个更好的初始提示词——干净的会话几乎总是优于一个堆满纠正的长会话。
   检查点：放心让它试错
   冒险方案不行就回溯换条路，检查点随会话保存，隔天依然可回溯。⚠ 但它只追踪编辑工具产生的改动——检查点不能替代 git。
   主动压缩
   任务之间清理上下文；定向压缩（“聚焦 API 改动”）；把“压缩时必须保留什么”写进规则文件。
   调研外包
   需要读大量文件的调研交给子智能体——在独立上下文里消耗，只回传摘要。
   即时纠偏
   发现跑偏立刻中断改向，上下文保留，可以马上换指令。越晚纠偏，成本越高。
   会话当分支
   每条工作流一个命名会话（如 oauth-migration），跨天继续不用重复解释背景。
   结论
   最好的结果来自紧密的反馈循环，而不是完美的第一版提示词。发现跑偏立刻纠偏——这是用 Agent 和用搜索引擎的根本区别。

== P27
   权限：先画笼子，再放它出去
   每次都弹窗确认，点过第十次你就不再是审查——只是在点
   两难
   全确认 = 安全但注意力疲劳，审查形同虚设；全放行 = 风险失控。真正有效的注意力是稀缺的，别消耗在低价值点击上。
   两条互补的解法
   权限白名单：具名放行你信任的操作 ｜ 沙箱隔离：限制文件系统与网络边界，让它在笼子内自由工作。
   四种权限模式
   自动复核
   独立模型替你拦风险操作，日常改动不弹窗
   手动确认
   写文件、跑命令前逐次询问——你想亲自批准时
   只读规划
   只能探索与出方案，不落任何修改——探索阶段
   预批准
   只放行具名工具，其余一律拒绝——无人值守批量
   沙箱隔离
   文件系统与网络必须有边界，不让它在主环境裸奔
   最小权限
   批量运行前具名声明放行工具，不做全量授权
   全程可审计
   能回答“它改了什么、执行了什么命令”
   危险动作人工闸
   数据变更、部署、密钥操作保留人工审批
   结论
   便利来自权限，风险也来自权限——顺序不能颠倒。

== P28
   规模化：从一个 Agent 到一条流水线
   先让一个智能体用得有效，再成倍放大——顺序反了，只会复制低效
   现场演示
   无头模式
   命令行非交互调用 + 结构化输出（JSON），接进 CI、提交前钩子与自动化脚本。
   并行会话
   在隔离检出中同时跑多个会话，改动互不覆盖；会话之间可传递发现。
   扇出迁移
   大迁移拆成批量任务：先 2-3 个小样试跑、调提示词，再全量——具名放行所需工具。
   无人值守
   自动复核模式下跑长任务；结束时由全新上下文的评审智能体做对抗式检查。
   流水线集成
   输出 JSON 供下游命令消费——让 Agent 成为数据处理管道中的一环。
   Writer / Reviewer 模式
   会话 A · Writer
   “为 API 端点实现限流器。”
   会话 B · Reviewer
   “审查这个实现：边界情况、竞态条件、与既有中间件范式的一致性。”
   会话 A · Writer
   “这是评审意见（粘贴 B 的输出），处理这些问题。”
   结论
   全新上下文的评审者不会偏向自己刚写的代码——多会话最大的红利不是速度，是质量。⚠ 被命令“找缺口”的评审者几乎必然报出缺口：明确只标记影响正确性的问题，把其余视为可选，警惕过度工程。

== P30
   团队落地：90 天，三个阶段
   先统一规则文件，再谈覆盖率——顺序不能颠倒
   第 1 个 30 天
   建规范
   规则文件 < 100 行 + 3 个高频技能 + 2 个确定性钩子。判定：新人照规则文件能跑通一次完整改动。
   第 2 个 60 天
   跑试点
   1-2 个真实需求的端到端案例（含 SPEC、diff、验证输出、评审记录）。判定：复盘能说清哪里省了时间、哪里把时间还回去了。
   第 3 个 90 天
   进流水线
   CI 中的无头调用 + 提交前钩子 + 权限白名单基线。判定：无人值守任务有失败告警，且有回滚路径。
   采纳率
   实际使用比例与频次——不好用的东西推广不动，这是前置指标
   返工率
   产出被人工推翻/重写的比例——直接反映上下文质量
   缺陷密度
   单位改动引入的缺陷数——防止“速度换质量”的自欺
   端到端时长
   需求提出到合入的墙钟时间——唯一能证明“整体更快”的指标
   结论
   只统计“生成了多少代码”会奖励错误行为——产出更多代码，从来不是工程目标。
